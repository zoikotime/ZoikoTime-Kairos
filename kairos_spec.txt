0. Document Purpose

This document is the complete production specification for Kairos, ZoikoTime's conversational intelligence layer. It supersedes prior
chatbot and assistant drafts. It defines what Kairos is, how it is built, how it behaves, how it is evaluated, how it is governed, and
how it ships.

The audience is not a marketing team only. This specification is for the teams that will build, secure, test, operate and
commercialise the capability: product, engineering, AI/ML, design, security, compliance, customer success, support, sales and
implementation.

 Zero-Gap Requirement

 No team should need to infer the intent of Kairos from a generic chatbot idea. This document resolves the product identity, surfaces,
 roles, permissions, data boundaries, tool actions, safety requirements, testing thresholds, rollout gates and acceptance criteria.

1. Executive Verdict

Kairos is a strong and strategically correct name. It aligns with ZoikoTime's thesis that the product is not merely about measuring
chronological time. ZoikoTime exists to help organisations understand meaningful work, workforce truth, productivity intelligence,
evidence integrity and operational accountability.

Claude's draft provided a useful foundation, particularly around the name, RAG architecture, permission boundaries, phased rollout
and evaluation discipline. This production version incorporates those strengths while tightening ZoikoTime-specific positioning,
enterprise safety, engineering implementability, support workflows, employee transparency and procurement-grade governance.

Kairos must be treated as a governed enterprise interface, not as a consumer bot. It must become a trust asset: accurate,
restrained, auditable, useful and role-aware.

2. Product Definition

Kairos is ZoikoTime's governed conversational intelligence layer. It is a permission-aware, source-grounded interface that helps
users understand, configure, adopt, operate and trust ZoikoTime.

Kairos is not a standalone product. It has no separate subscription, no separate customer portal and no independent brand outside
the ZoikoTime ecosystem. Kairos inherits identity, workspace context, permissions and policy constraints from ZoikoTime and
Zoiko Connect.

2.1 What Kairos Must Do

 Answer public product, pricing, use case, trust and demo questions on zoikotime.com.
 Guide logged-in customers through setup, reports, troubleshooting, policies, roles, billing routes and support escalation.
 Explain employee-facing transparency, personal data, screenshots, idle time, breaks, correction and dispute workflows.
 Support admins with policy-based configuration, reports, audit logs, legal hold overview and implementation routing.
 Operate inside Zoiko Connect where authorised, including mention-based help, action extraction and permission-scoped

      workforce summaries.
 Escalate cleanly to humans when legal, security, billing, support, procurement or implementation judgement is required.

2.2 What Kairos Must Not Do

 Act as a general-purpose AI assistant.
 Provide legal, HR disciplinary, medical, tax or financial advice.
 Encourage hidden, covert or non-transparent workforce monitoring.
 Invent product features, certifications, customer commitments, pricing exceptions or roadmap items.
 Access data outside the user's workspace, role or consent boundary.
 Replace human sales, support, legal, security or implementation teams.

Approved product name: Kairos.
Meaning: Kairos is the concept of qualitative, meaningful or opportune time. This is strategically superior to a generic assistant
name because ZoikoTime is not a stopwatch. It is a workforce assurance and performance intelligence platform.

8.1 Processing Flow

1. User submits query from a surface.
2. System resolves user state: anonymous, authenticated, admin, employee or Connect user.
3. Intent classifier assigns category and confidence.
4. Permission context generates effective retrieval and tool scope.
5. Retriever returns only approved source chunks within scope.
6. Tool planner selects action only if needed and authorised.
7. Generator drafts response using retrieved context and tool results.
8. Validator checks grounding, safety, permission boundary and tone.
9. Response is rendered with citations, quick actions and escalation route.
10. Logs are written for conversation, retrieval, model, tool, safety and analytics.

13. Safety and Guardrails

13.1 Refusal Categories

 Legal advice, litigation advice or wage and hour compliance determinations.
 HR disciplinary recommendations, termination recommendations or performance punishment advice.
 Covert monitoring, transparency bypass, audit log bypass or report manipulation.
 Requests for another user's data or another workspace's data.
 Internal system prompt, hidden instructions, model configuration or security internals.
 Internal roadmap, vulnerability details, private customer configurations or pricing exceptions.
 Off-topic general AI tasks outside ZoikoTime scope.

13.2 Prompt Injection Defence

 Treat all user input as untrusted data.
 Never expose system instructions or hidden policy text.
 Strip or neutralise instructions embedded in retrieved content.
 Validate tool calls with schemas and central authorization.
 Detect jailbreak patterns, role-play attacks and "ignore previous instructions" attempts.
 Rate limit persistent adversarial behaviour and log security events.

interaction data and must not be silently linked to later authenticated identity without explicit consent.

22. Engineering Build Notes

22.1 Recommended Stack Principles

 Use RAG, not a free-form chatbot.
 Use a typed tool layer, not open autonomous agent loops.
 Use provider-agnostic orchestration.
 Own the retrieval pipeline for residency, permission and vendor flexibility.
 Version prompts, knowledge, tools and evaluation sets.
 Log all model and tool calls.
 Validate all outputs before rendering.
 Do not cache user-specific responses.
 Do not let the model decide permissions.
 Do not expose internal instructions.

22.2 Failure Modes           Required Behaviour

 Failure                     Fall back to search/help articles and human escalation.
                             State knowledge access issue; do not answer from memory.
  Inference provider outage  Acknowledge failure; offer retry or human route; do not claim success.
  Retrieval failure          Ask one clarifying question.
  Tool failure               Offer human escalation proactively.
  Ambiguous query            Refuse or route safely; log event.
  User frustration           Deny access and explain boundary without revealing restricted detail.
  Safety violation detected
  Permission conflict

23. Explicit Exclusions From v1 Launch

 Voice interface.
 Fully autonomous multi-step actions without confirmation.
 Long-term personal memory by default.
 Third-party plugin marketplace.
 External customer API for Kairos.
 Image generation.
 Legal compliance determinations.
 HR disciplinary recommendations.
 Unapproved employee surveillance workflows.
 Direct editing of billing, pricing, retention, legal hold or security settings without permissioned workflow and confirmation.

24. Operational Runbooks

24.1 Critical Incident Runbook

 Detect: automated alert or user/internal report.
 Triage: classify as safety, privacy, permission, hallucination, outage or abuse.
 Contain: disable surface, model, prompt version, retrieval source or tool as required.
 Notify: Product, Engineering, Security, Compliance and Support owner.
 Investigate: preserve logs, source versions, prompt versions and tool history.
 Remediate: patch content, prompt, tool, permission rule or model config.
 Validate: run regression and targeted red-team tests.
 Document: post-incident review with root cause and prevention steps.

24.2 Knowledge Staleness Runbook

 Daily job flags expired sources.
 Expired sources are excluded from retrieval if outside SLA.
 Owner receives task to review or deprecate.
 Updated article triggers re-indexing and evaluation sample update.
 Repeated stale sources appear on compliance dashboard.
